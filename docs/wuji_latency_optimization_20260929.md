# Wuji 低延迟改动与验证

## 已完成的改动

1. 新增 `/api/wuji/frame`：后端取可信最新骨架、校验序号与龄期、求解并更新控制目标，随后一次返回骨架与求解结果。浏览器不再先取骨架、再用 `/api/frame` 交回同一骨架。浏览器请求仍用于驱动输入更新和会话存活；本次没有增加脱离页面独立运行的控制会话。
2. 同一骨架版本只求解一次，不刷新旧控制目标的时间；无效输入保持限频处理，重新连接后的新帧可以恢复预览。
3. 新链路按约 8 ms 请求节奏调度，耗时已超过周期时不再额外等待 16 ms。读取 node0 的最新帧周期由 1/60 秒改为 1/120 秒，耗时与缓存龄期改用高分辨率 `perf_counter()`。
4. A3.2 控制线程使用独立的 Windows 高精度可等待计时器。系统不支持或调用失败时回退到 Event.wait；关闭等待有界，句柄在退出时释放。该 API 的支持范围与行为见 [Microsoft 官方说明](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw)。
5. 同一控制采样的 SDK 状态复用于记录，减少重复读取；没有开启记录时跳过原始帧记录对象构造和深拷贝。
6. 控制状态、成功采样和原始 SDK 日志新增 `control_timing`，记录锁等待、SDK 状态读取、规划/记录、编码/写入耗时，便于定位真机抖动。
7. 前端通过创建接口的 `combined_frame` 能力字段选择新路径。尚未重启的旧后端继续走原路径，避免新静态文件与旧进程不兼容。
8. 页面关闭或切换输入取消 HTTP 响应时，服务关闭该连接，避免再次向已断开的 socket 写入 500 响应；序列化和求解错误仍正常报告。

速度、加速度、jerk、碰撞距离及路径检查、失联保护均保留。延迟的控制采样仍最多推进 5 ms，避免积压后一次大幅追赶。两路 A3.2 MIT 减速比仍为用户要求的 50。

## 性能对比

### 浏览器链路 A/B

使用 100 Hz 合成骨架、真实本地 HTTP 服务、A3.2 withid 求解器和 Chrome。旧路径模拟独立的 16 ms 轮询及只保留最新帧的求解队列；新路径使用合并接口。两组均使用当前求解器及同一个 120 Hz 上游读取实现。每组 7 秒，去除前 1 秒；顺序运行，不能排除热缓存与调度噪声。

| 指标 | 原浏览器路径 | 合并路径 |
|---|---:|---:|
| 完成帧率 | 52.3 Hz | 77.8 Hz |
| 回调至响应延迟上界中位数 | 20.36 ms | 19.05 ms |
| 同项 95 分位 | 38.73 ms | 35.13 ms |
| 单帧请求处理时间中位数 | 13.60 ms | 11.90 ms |

帧率提升约 49%，95 分位延迟下降约 9%。这是 localhost 合成输入测试，不包含真实手套内部处理、Windows/node0 网络以及机械手到达目标的时间，不能视为真机总延迟。

脚本：`online_control/online_motion_track/tests/wuji-latency-benchmark.mjs`。
数据：`logs/wuji_validation/latency-ab-20260929.json`。

仿真 SDK、真实 A3.2 机构换算、重定向、Mink、逐采样碰撞检查和磁盘记录同时运行 6 秒：

- 下发频率约 199.8 Hz，完成 338 次求解，结束时无控制错误。
- 控制周期中位数 5.007 ms、95 分位 5.657 ms、最大 10.57 ms。
- 锁等待中位数 0.0014 ms、95 分位 1.619 ms。
- SDK 状态读取中位数 0.282 ms；规划/记录中位数 0.592 ms；模拟编码/写入中位数 0.437 ms。

数据：`logs/wuji_validation/a32-loaded-20260929.json`。测试没有连接或使能实体硬件，因此不等同于复现并解决此前真机 65 Hz 的全部成因。

## 真机验证

相关 Python 测试 90 项、JavaScript 测试 10 项通过；Chrome 完成合成手套到真实求解器的链路测试，覆盖左右手、过期、恢复、停止与切换输入。测试未开启实体机械手。

用户接回手套后复查：Windows WLAN 地址已由 `192.168.88.27` 变为 `192.168.88.65`，node0 路由地址仍为 `192.168.88.10`。已通过可信 SSH 更新 node0 的 `bridge.env` 为 `--address 192.168.88.65:50001`，重启采集服务并读回确认。原配置备份在 node0 的 `~/wuji-glove-bridge/bridge.before-network-auto.env`。

Windows 的以太网接口 16 仍显示 `Disconnected`，保留 `192.168.1.50` 地址；node0 左手状态为连接超时。本地旧 UDP 转发器仍绑定 `192.168.88.27:50001`，旧网页服务也尚未加载本次后端优化。之前停止并重启本地服务的操作被自动审批拦截，未尝试绕过。

因此尚未进行真实手套延迟对比。网口恢复后，由用户运行 `start_local_and_update_node0.cmd --local-only`：脚本会重新检测地址、校验防火墙、同步 node0，再停止旧服务并启动新服务；页面使用 Ctrl+F5 刷新。记录完整一次真机操作，检查 `control_timing`、源数据龄期与 SDK 错误，才能确认实际延迟与动作完成时间。

不得仅凭帧率提高就放宽速度或碰撞限制。若复杂姿态下持续错过 5 ms 周期，新增分段计时将用于判断是否需要将求解从控制进程中隔离。
