# Wuji 链路断流与延迟排查（2026-09-29）

## 结论

问题来自两个环节：Windows 与 node0 间的无线传输会超时，网页之前又同步等待每次远端取数；本地 Mink 避碰检查也有明显的长尾耗时。已经部署后台取数、HTTP 连接复用及避碰计算优化。仍有无线网络丢包和 SDK 心跳超时，尚不能认为断流已根治。

当前数据路径：手套 → Windows 专用以太网 → Windows WLAN → node0 WLAN/SDK → Windows 网页后端 → 浏览器。Windows 和 node0 之间的两段骨架/原始数据传输均经过无线网络。

## 已部署的修改

1. Windows 后台持续读取最新 SDK 骨架，网页接口只取本机缓存，不再等待一次 node0 网络请求。
2. node0 HTTP 服务支持持久连接并禁用 Nagle；客户端复用连接，失败后自动重建。
3. 缓存时间始终累计；一次请求失败不会重新赋予旧帧新时间。350 ms 过期、序号检查、退役流检查和会话绑定继续生效。
4. 增加 transport 分段耗时及错误计数；控制记录增加 `source_to_response_upper_ms`，便于区分输入龄期和求解耗时。
5. Mink 在精确距离判断前排除包围球已经确定分离的胶囊对；遇到违反间距的几何对立即结束可行性判断。间距、路径采样、QP 和最终输出距离检查保留。

## 实机复测与尚存问题

新版已运行在 node0 与 Windows 8766。60 秒预览测试使用真实左手套和相同型号，未连接/使能机械手：

- 2746 次本机输入轮询，2704 次有效（98.47%）；仍有 42 次无新鲜骨架。
- 891 次求解返回，879 次跟随成功。
- 本机取数耗时：中位 5.19 ms，95% 分位 8.80 ms，最大 16.32 ms。
- 后端输入龄期：中位 36.2 ms，95% 分位 226.3 ms，最大 525.4 ms。
- 总求解耗时：中位 53.5 ms，95% 分位 86.9 ms，最大 265.5 ms。
- 浏览器 JavaScript 错误 0；测量末远端 HTTP 错误累计 20 次（含预热阶段）。

复测没有重放相同的手部运动，也关闭了浏览器录制，不能把它与用户记录当作严格的整链路 A/B 性能实验。

复测启动阶段，node0 在 15:09:40–15:09:42 连续三次心跳超时并断开设备，15:09:45–15:09:46 重新连接。SDK 日志也有 `emf_poses lagged`。这一次明确捕获到了实际 SDK 断连；仅凭日志无法把所有 SDK 排队都归因于 Wi-Fi。

另一次 20 包 ping 中收到 19 包，1 包超时；已收到包往返 5–25 ms。小样本不能作为长期 5% 丢包率估计，但说明无线链路存在瞬时不可达。Windows 为 5 GHz Wi-Fi，显示信号 100%；node0 路由确认使用 wlo1。因此“信号强”并不能排除这里的传输抖动。

## 下一步处理优先级

1. **优先将 Windows ↔ node0 改为同一有线局域网。** 手套继续占用 Windows 现有专用网口；Windows 可用第二块以太网适配器连接交换机，node0 的有线网口也连接该网络。要让实际数据路由走有线，仅插上不在同一网络的网线不够。
2. 更换地址后同步修改启动参数 `--quest-host` / `--wuji-windows-host` / `--wuji-node0-host`、Windows UDP 规则，以及 node0 `bridge.env` 中的监听地址和设备入口，再重启服务。当前 IP 配置保留在启动脚本中。
3. 有线连接完成后再采集至少两分钟的开合、捏合记录，分别检查网络失败、骨架龄期、求解和实际下发。先消除传输长尾，再考虑进一步优化 retarget 或将求解与高频控制分进程。

不建议通过提高过期阈值或关闭避碰来掩盖问题。
