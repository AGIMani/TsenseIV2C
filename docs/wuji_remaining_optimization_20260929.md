## 优先顺序

### 1. 先解决实际控制频率与规划时间不匹配

当前目标为 200 Hz，但那次运行约 65 Hz。每轮只推进最多 5 ms，是此前为避免延迟后的突然追赶而保留的保护。这意味着该记录中每秒墙钟时间只推进约 0.325 秒规划时间，可能明显拉长动作。

下一步应分别测量控制锁等待、轨迹与采样碰撞检查、机构换算、SDK 状态读取/序列化、记录事件的耗时。控制器的 `step`、输入更新和状态快照共用锁；仅凭现有总周期无法确认其中哪一步主导耗时。优先减少重复读取和锁占用，必要时将求解与控制分到独立进程。若需要随实际时间推进，应逐个验证中间轨迹样本及速度/加速度限制，不能直接把延迟累积成一次大的电机跳变。

### 2. 让 Windows 后端直接消费手套帧

当前有两次轮询：Windows 后端按约 60 Hz 拉取 node0 最新帧，浏览器请求最新帧后再等 16 ms，然后把骨架交回本地 `/api/frame` 求解。可以让已绑定会话的 Windows 后端直接消费最新帧并更新目标，页面只接收显示结果；保留会话授权、心跳、过期帧校验和断线停止逻辑。这样有望减少一次页面往返及轮询等待，收益需实测。

node0 到 Windows 也可改为持久推送，但应保持只保留最新帧，防止可靠传输在重连后堆积旧动作。

### 3. 针对求解耗时的峰值做分析

Mink 通常很快，但这次最大约 55 ms。可以通过日志回放定位具体姿态，检查迭代次数、重复几何更新与距离查询。必须保留完整最终距离校验，不能再通过缩短网格查询范围来提速。总求解中位数约 12 ms，说明也需要分析重定向和其他处理的耗时。

### 4. 补齐可用于归因的计时

Wuji 传输线程仍使用本机分辨率约 15.6 ms 的 `time.monotonic()`，导致 HTTP RTT 统计出现 0/16 ms 的台阶；可改用 `perf_counter()` 做进程内耗时测量。再记录同一帧的后端接收、求解完成、控制线程选中、写入完成时间，才能准确比较改动前后。跨机器时间应区分时钟同步误差与真正网络时延。

本次仅完成评估，没有调整轨迹速度、碰撞保护或采样策略。减速比按用户最新要求恢复为 A3.2 两路 MIT 均 50，正反换算和状态标注同步恢复；18 路 self 的机构换算保持原定义。
