# 21 点标定与拇指根部连杆选择

## 网页动态标定页面

手势跟踪网页右上角新增“动态标定”入口，也可直接访问同一服务的 `/calibration`。支持 A3.0、A3.2 及各自 with ID 的左右手，沿用所选模型的 URDF、21 点标定和求解参数。

三栏依次为可编辑输入骨架、URDF 零位静态标定、实时求解后的模型。输入初值等于静态标定的零位世界坐标；拖动第一栏或修改第二栏的点与所属连杆后，第三栏立即重新求解。坐标框以毫米显示，输入坐标属于 URDF 基坐标系，标定坐标属于所选连杆。更换连杆时会换算局部坐标，保持点的世界位置。可勾选吸附所属连杆表面，也可拖动 XYZ 轴做空间调整。

关键点来源复用手势跟踪页面的三种接入：

- **MediaPipe 相机**：使用同一个浏览器 Worker 和识别模型，摄像头由访问网页的电脑直接采集。此路径不经过桌面 Qt 编辑器的 Linux `/dev/video0` 相机链路。
- **Quest WebXR**：使用原有配对、25→21 点映射、数据过期判断及 `/api/webxr/*` 接口。电脑与头显须访问同一可信 HTTPS 服务。
- **Wuji 数据手套**：使用服务既有 SDK / HTTP 桥接配置、手别选择、21 点转换及 `/api/wuji/*` 接口。

“接入实时输入”持续更新第一栏，第二栏仍可拖动并参与求解；“停止 / 冻结”保留当前骨架，可继续手动拖点或应用四种对指、半握拳、握拳、钩拳、零位及 Kapandji K1–K10。预设与桌面版共用实现，紫色点表示骨架估计的目标位置。采集手别可独立选择；输入按掌宽缩放、腕部对齐到模型。对齐参考在每次接入时固定，编辑静态标定不会挪动已有输入骨架。切换采集源需先冻结。

求解使用当前页面内存中的标定，按最新输入替换待处理帧；冻结后的手动姿态会继续有限次暖启动求解。未检测到所选手或输入过期时保留最后骨架并显示状态。浏览器隐藏页面时自动冻结输入。这里显示原始标定求解结果，不接实机控制、碰撞过滤或 Ruckig。

“保存标定”仅写入当前型号、手别的标定 YAML，先备份旧文件，再原子替换。其他编辑器/页面改过该文件时会拒绝覆盖，可先导出草稿再重新加载。输入姿态不保存到标定文件；“重新加载”保留输入骨架，只刷新静态标定。“导出 YAML”支持下载草稿，公共服务只开放导出。保存后重新创建手势跟踪会话即可使用新标定，已开启的其他会话仍保留自己的原始配置。

网页预览与桌面编辑器共用 `tools/keypoint_preview_solver.py`，服务使用 NumPy 运动学后端，无需 Qt。开发验证：

```bash
python -m pytest -q tests/test_web_calibration.py
cd online_control/online_motion_track
HAND_PYTHON=/path/to/python npm run test:calibration
```

浏览器测试使用合成相机/Quest/手套输入验证链路，并把保存操作重定向至临时目录，不修改项目标定文件。首次运行需安装 Playwright Chromium（`npx playwright install chromium`），或用 `CHROME_PATH` 指定已有浏览器。

## 三视图实时标定工作台

`tools/edit_robot_keypoints_21.py` 默认三维模式并排显示三个视图：

1. **输入关键点**：21 点从打开文件时的当前零位标定初始化。可拖动编号点、XYZ 手柄，或在下方输入基座坐标（mm）。该输入独立于标定；调整中间标定时保持输入姿态，便于比较结果。“输入重置为当前标定”可重新复制中间的点。
2. **静态标定 / URDF 零位**：保留原来的点拖动、link 局部轴、Shift 点击贴面、连杆切换和保存操作。右侧面板编辑本视图；局部坐标以 mm 显示、以 m 保存。
3. **实时 retarget**：使用同一型号、手别和 URDF 的完整原始网格，显示最新输入与内存中标定的求解结果。标定不必先保存；位置及 link 修改会同时刷新 FK、解析雅可比、掌宽和拓扑参考系。

三个视图均可独立旋转、平移、缩放和切换轴向视角。左侧 XYZ 手柄沿基座轴；中间 XYZ 手柄沿所选 link 的局部轴。右侧仅查看求解结果，不能拖动输出点。

在当前 WSL 开发环境，从 PowerShell 启动 with ID 左手：

```powershell
wsl.exe -d Hand-Ubuntu-24.04 --cd /home/onkiall/projects/hand -- bash -lc '~/.venvs/hand-gui/bin/python tools/edit_robot_keypoints_21.py --model TsenseI_v3_2_withid --hand-side left'
```

裸手使用 `--model TsenseI_v3_2`；右手使用 `--hand-side right`。原生 Ubuntu 可在项目根目录直接执行同一 Linux Python 命令。`--view 2d` 仍打开原来的双投影视图，不含实时预览。

建议先在左侧摆出屈指或捏合目标，再修改中间的指尖、关节代理点或所属连杆，对比右侧结果。后台求解采用该型号 profile 的参数及 URDF 关节限位，以最新输入替换积压请求；每次编辑后继续 warm-start 求解，连续三帧关节变化小于 `1e-5 rad` 时暂停，最多预览 60 帧。右下角显示状态和耗时，悬停可查看关节弧度。失败或尚在求解时明确标记，保留上次结果。

这是重定向标定预览，不含碰撞过滤、Ruckig 或实机下发。稳定只表示相邻帧关节变化足够小，不保证输入点逐点重合或全局最优。保存仍只写标定 YAML 并备份原文件；左侧试验姿态不写入标定。Reload YAML 更新中间标定并重新求解，左侧输入保持不变。

### 常用骨架与 Kapandji 目标

左侧视图下方的“常用标定骨架”提供半握拳、握拳、钩拳、标定零位，以及拇指与食指／中指／无名指／小指四组对指。屈指预设弯曲四指，保留拇指参考姿态。下拉选择 K1–K10，点击“应用 K 点”即可生成对应输入姿态。

目标顺序采用 [Kapandji 1986 年原始定义](https://pubmed.ncbi.nlm.nih.gov/3963909/)：

| 目标 | 接触位置 |
|---|---|
| K1 / K2 | 食指中节桡侧 / 末节桡侧 |
| K3–K6 | 食指尖、中指尖、无名指尖、小指尖 |
| K7 / K8 / K9 | 小指 DIP 掌侧纹、PIP 掌侧纹、指根掌侧纹 |
| K10 | 掌部远侧横纹（小指侧） |

这些是**可编辑的几何目标预设**：21 点骨架没有皮肤表面和掌纹，K1/K2 以指节中点向桡侧偏移估计，K7–K9 以对应关节点向掌侧偏移估计，K10 以小指 MCP 向腕部移近的位置估计；不是实测人体姿态或自动 Kapandji 评分。

每次应用从当前中间标定重新生成，固定腕点及各指根、保持原骨节长度；按模型食指 MCP 屈曲方向确定掌侧，以适配不同 CAD 坐标和左右手。对指时弯曲目标手指，并用固定骨长的拇指链逼近目标。紫圈标记输入接触目标，超出骨长可达范围时显示剩余距离，不拉长骨节强行接触。该距离属于输入骨架，不是右侧机器人的实际接触误差。

应用预设会立即触发实时求解，不修改中间标定或磁盘 YAML。随后调整中间标定仍保留当前输入。拖动输入点进入自定义姿态并清除紫圈；再次选择预设会从当前标定重新生成，不累积上次弯曲。

### MediaPipe 实时输入

左侧预设区下面新增 MediaPipe 接入控件：

1. 填写本机摄像头索引（例如 `0`）、Linux 视频设备（例如 `/dev/video0`），也可填写视频文件路径。
2. 选择“识别左手”或“识别右手”，点击“接入 MediaPipe”。程序只接收所选手的有效 21 点 **world landmarks**；不把归一化图像 Z 当作米制三维点。
3. 第一栏实时显示输入骨架，第三栏随之求解。中间标定可以继续调整；左侧预设、坐标编辑和拖点暂时禁用，视角旋转和缩放仍可操作。
4. 点击“停止 / 冻结”释放相机并保留最后输入，随后可以拖点或选择预设。关闭编辑器也会停止采集。

采集复用项目的 `WujiMediaPipe21` Tasks 识别器及 `hand_landmarker.task`，采用现有摄像头链路的 raw Left/Right 标签约定（`swap_handedness=False`）、轻量平滑，关闭 Wuji 固定骨长修正。输入按腕点平移、掌面方向旋转、掌宽统一缩放到当前标定参考系；选择另一只手时，在掌部局部深度轴做镜像以匹配当前 URDF 手别。模型与标定文件的手别不改变。对齐参考在每次接入时固定，编辑中间标定不会偷偷改变同一人手姿态的输入参照；重新接入时使用最新标定。

相机和识别在独立进程中运行，至多保留一份最新点数据，不向 Qt 队列堆积视频帧。丢手、错误手别、无效骨架、缺失 world landmarks 或数据超过一秒时保留最后输入并显示状态；退出或设备读取卡住时可终止本编辑器拥有的采集进程。实时状态允许显示同一标定的稍早求解帧，以避免检测快于求解时输出一直不更新；旧标定的结果仍会丢弃。

此入口使用**运行编辑器的 Linux 环境**所能访问的摄像头，不使用浏览器的摄像头权限。WSL 需要先通过外部设备直通等方式让 Linux 识别视频设备；原生 Ubuntu 直接使用本机设备。没有修改 WSL 桥接或系统设备配置。摄像头优先请求 **640×480 MJPEG / 30 fps**，状态文字显示设备实际协商的分辨率和格式；文件输入沿用视频本身的格式。30 fps 是请求值，不是实际处理帧率保证。

2026-10-01 现场检查：内置相机 `5986:2137` 已经由 USB/IP 接入 `/dev/video0`，驱动为 `uvcvideo`。旧入口采用 640×480 YUYV，原图大部分为绿色缺失区域，6 次抽查均未检测到手；640×480 MJPEG 原图完整且 6 次抽查均检测到左手；1280×720 MJPEG 原图再次出现大面积损坏。此对比说明当前设备／USB 直通采集组合存在格式相关的破帧问题，不能归因于关键点标定；尚未通过 Windows 原生采集对照把原因进一步定位到具体驱动或 USB/IP 层。

改为优先 MJPEG 后，使用正式 `open_capture` 连续读取 120 帧无读取失败，耗时约 8.49 秒；抽查的 21 帧中有 19 帧检测到左手并通过输入门禁。完整画面仍有灯光泛白，属于后续光照／成像质量调整范围。这是短时实机验证，不代表长期稳定性验收。诊断原图和统计保存在本地 `.work/camera-diagnosis/`，没有上传。

## 一键同步所有模型右手标定

左手标定保存后，在项目根目录双击 `sync_all_right_keypoints.cmd`，或运行：

```powershell
.\sync_all_right_keypoints.cmd
```

只检查并预览改动：` .\sync_all_right_keypoints.cmd --dry-run`。也可使用当前 Python 环境运行 `python tools/sync_all_right_keypoints.py`。

脚本遍历当前 `PROFILE_PATHS` 中的全部模型，各模型只读取自己的左手 21 点文件。V3.0、V3.0 with ID、V3.2 with ID 沿 Y 轴镜像；V3.2 裸手沿 X 轴镜像。V2 右手求解器共用左手标定，自动跳过复制。各模型独立，裸手和 with ID 不交叉覆盖。

全部输入通过检查后才开始写入；有变化的右手文件先备份为 `.bak_时间戳`，相同内容跳过。同步会覆盖右手单独调整过的标定，备份保留原值。仅同步关键点，不重建 URDF 或碰撞模型。完成后重启本地服务；node0 需要重新部署。

21 点标定是在机器人上定义与 MediaPipe 21 个解剖关键点相对应的位置。它不是把 21 个点逐一分配给 21 个电机，也不是直接给定关节角。

每个点由 `link`（所属刚体）和 `local_xyz`（该刚体局部坐标）定义。正向运动学由候选关节角计算 21 点的位置；重定向优化再比较人机骨向、点间关系和交互拓扑，迭代求出机器人角度。`local_xyz` 错误会改变骨长/方向/指尖位置；`link` 错误会改变点随哪些关节运动，并改变求解雅可比。

在 `TsenseI_retargeting/fk/fk.py`，计算为 `world = link_poses[kp.link] @ local`。机器人有多少执行关节与标注点数量不必相等；一个点可以同时约束多个上游关节，一个关节也会影响多个下游点。

## V2 拇指的四个关节

```text
base_link
  └─ thumb_rota_link   ← thumb_rota_joint
      └─ thumb_swing_link  ← thumb_swing_joint；当前 CMC 代理点
          └─ thumb_MCP_link  ← thumb_MCP_joint；MCP 点
              └─ thumb_PIP_link  ← thumb_PIP_joint；IP 点、指尖
```

rota、swing 提供根部不同轴向的旋转，MCP、PIP 提供后续弯曲。所有下游点都会继承 rota 的运动，不需要专门给 rota 增加一个 MediaPipe 点。

CMC 是解剖语义/代理点，不等于某个机械关节名称。下表只讨论 **CMC 标注点** 的绑定；MCP、IP、指尖仍需保留正确的近节/末节归属。

| CMC 绑定 | 跟随 rota | 跟随 swing | 跟随后面的 MCP/PIP |
|---|---|---|---|
| thumb_rota_link | 是 | 否 | 否 |
| thumb_swing_link | 是 | 是 | 否 |

应先确定 CMC 代理点在机器人上代表哪个位置：若它位于 swing 转轴上游的基座，就绑定 rota；若它代表 swing 后的运动结构，则绑定 swing。若点恰好在 swing 旋转轴线上，两种表达可具有相同轨迹。不能仅按名字或静止截图选择，也不能改 `link` 后沿用旧 `local_xyz`；应通过完整坐标变换保留标定姿态的位置。

## 当前项目的选择与证据

当前 V2 保留 `thumb_swing_link`。上一轮修复将 CMC 从 MCP 连杆移到 swing、MCP 从 PIP 移到 MCP，消除了下游弯曲带着上游标记运动的问题，并保留全零位置。这个修复证明了原绑定有错，但并不构成“swing 对所有姿态一定比 rota 好”的证明。

2026-09-18 对 CMC 单独做 A/B：将它换算到 rota 局部坐标，保持零位世界位置一致，其他标注及新实时参数相同。使用 09-17 记录的帧 18211–18511，碰撞开启、相同暖启动和回灌；剔除前 60 帧后，筛选人手 IP 弯曲大于 0.6 rad 的 95 帧：

| CMC 绑定 | IP 几何角误差中位数 | 拇指尖到中指尖距离中位数 |
|---|---:|---:|
| swing（当前） | 5.90° | 20.39 mm |
| rota（候选） | 7.09° | 21.11 mm |

这段对指样本支持暂时保留 swing，但差异较小。不开碰撞的另一对照中，rota 的整体骨向/拓扑损失略低，而 swing 的末节角度误差较小，说明不能只选一个总损失判断标定优劣。距离越小也不总是越好，仍需检查人手目标与指腹接触几何。

因此当前推荐：**V2 继续使用 swing；若要改为 rota，应依据实际机械位置重标定，并用展开、握拳、食指/中指对指多组动作验证。** 本次没有修改 CMC 绑定，候选文件只保存在 `logs/v2_response_20260918/keypoints_cmc_rota.yaml`。

V3.2 有独立的机械关节链与标定文件，CMC 使用 `thumb_rotaback_link2`，不能套用 V2 的连杆名称来决定绑定。
