# A3.2 真机下发间隔与相邻目标变化检查

## 结论

本次真机日志不满足每包 1～4 ms。当前控制周期配置为 5 ms，实际连续成功下发约 121.75 Hz。延迟的主要证据是上位机调度与计算耗时；本次 SDK 没有报告发送失败或断连。

本报告读取 18:53～18:55 的已结束日志；没有重放命令、使能硬件或修改运行服务。周期参数仍为 5 ms，尚未实施或验收严格 1～4 ms 的发送架构。

## 数据来源与测量范围

- 后端：`online_control/online_motion_track/logs/hand_control_20260929_185355_983094.jsonl`。
- 浏览器：`C:/Users/ONKIALL/Downloads/hand_control_20260929_185351_258000.jsonl`。
- 可复算结果：`logs/wuji_validation/a32-packet-timing-185355.json`。
- 分析脚本：`tools/analyze_a32_packet_timing.py`。

后端记录 9,328 次成功提交，含一次起步姿态提交及 9,327 次常规控制提交。下面统计常规提交之间的 9,326 个间隔，未按长短删除异常间隔。

后端时间来自成功调用 SDK 后捕获日志事件的 QPC 时间。浏览器样本携带 SDK 成功后发布样本的主机墙钟时间，不能使用浏览器批量接收日志的 `t` 计算发送频率。这两种指标分别包含日志构造和样本发布的开销，均不是 USB 线上抓包时间、固件收包时间或 CAN 电机接收时间。统计结论是当前主机提交链路不满足要求；目前数据不能用于验收设备收包的硬实时范围。

## 相邻包差值

常规成功提交之间，关节目标最大变化为 **0.0100 rad，约 0.573°**。按每对相邻整手包中的最大通道变化统计：

| 单位 | 中位数 | 95 分位 | 最大值 |
|---|---:|---:|---:|
| 直线通道 mm | 0.01358 | 0.11263 | 0.13380 |
| 旋转通道输出轴 deg | 0.04097 | 0.56680 | 0.57296 |

这与现有最大角速度 2 rad/s、每次最多推进 5 ms 相符；swing 通道最大角速度为 1 rad/s。没有看到超出这个量级的相邻关节跳变，但包间抖动依然会导致运动不均匀。直线、旋转和原始电机轴编码值必须按各自单位比较，不能混用一个绝对差值阈值。两路 MIT 减速比仍为 50。

| 阶段 | 中位数 | 95 分位 | 最大值 |
|---|---:|---:|---:|

| 规划、采样碰撞检查及状态记录 | 1.067 ms | 3.997 ms | 27.095 ms |
| 目标转换、再次读取状态及写入 | 1.258 ms | 2.331 ms | 3.650 ms |
| 骨架重定向与避碰求解 | 24.862 ms | 35.987 ms | 273.244 ms |
| 浏览器记录的源数据至响应上界 | 51.600 ms | 69.834 ms | 315.653 ms |

各阶段分位数不是同一批慢样本，不能直接相加解释端到端 95 分位。源数据至响应指标为保守上界，不含机械执行到位时间。

SDK 状态抽样中 `last_send_duration_ms` 中位数约 0.167 ms；本次累计最大 `sendOnce()` 耗时为 0.9973 ms。最终计数为 9,328 次成功、0 次失败、0 次断连。前者是抽样分布，后者的累计最大值覆盖原生封装记录的调用；都不能被解释为相邻包间隔。

实际连续控制时间 **76.5976 s**，同一范围内 Ruckig 累计推进 **45.9963 s**，轨迹时钟与墙钟比例约 **60.05%**。原因是迟到时仍使用 `min(dt, 5 ms)`；未推进的时间不进行一次大幅补偿。它限制了相邻包步进，但也明确拉慢轨迹推进。该比例不是每个手势的实测速度折扣，静止、目标变动和避碰也会影响实际运动。

后续修复及离线验证见 [A3.2 下发修复记录](a32_downlink_fix_20260929.md)。本文数据为修改前的真机基线。

## 满足目标需要的改变

1. 以 2 ms 为候选发送周期，将定时发送与骨架求解、JSON 日志、网页状态请求隔离。需要保持整手目标的原子快照，不能让两个通道集合在更新途中被发送线程读取。
2. 定时发送使用经过速度、加速度、jerk、机构和碰撞检查的连续轨迹样本；缓冲必须短且有界，并定义欠载、目标过期、停止、断连时的行为。单纯重复发送旧目标，无法解决动作跟随变慢。
3. SDK 的 `startStream(500)` 是可用连续发送入口，但本地 SDK 文档明确说明它不自动生成平滑轨迹，不代表整个系统以 500 Hz 运行。当前 Python 封装调用的是 `sendOnce()`。直接打开 SDK stream 而不协调样本生成、通道一致性和停止流程，不足以满足两个要求。
4. 在原生发送边界记录每包的单调时间、序号、相邻差值、超时和缓冲欠载计数；使用 USB/网络抓包或固件接收时间验证实际收包间隔。若目标是 H7 到 CAN 电机，还必须取得该段的时序证据。
5. 普通 Windows 用户态线程会受调度、锁等待及 I/O 影响。独立 C++ 线程可减少 Python 开销，但不能仅凭 500 Hz 参数保证每包始终在 1～4 ms。硬性截止时间要求应在具备实时能力的发送端/控制器及通信链路上实现并验收。固件定时插补能稳定电机更新周期，但不能反向保证 Windows 到 H7 的收包间隔。

不能仅将 Python 的 5 ms 改成 2 ms：若计算和调度仍需 8 ms，而每次只推进 2 ms，轨迹推进会进一步变慢。也不能通过迟到后连续突发发送来掩盖问题，那可能违反至少 1 ms 的包间隔。
