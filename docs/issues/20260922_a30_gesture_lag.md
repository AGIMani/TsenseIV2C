# A3.0 手势到模型跟随缓慢：分段定位

结论：这次主要滞后发生在 **手势目标 → Ruckig 输出**，其次是关键点低通滤波和视觉目标更新频率。串口提速不能消除已经存在于模型目标链路中的约四分之一秒跟踪滞后。

分析依据：`C:/Users/ONKIALL/Downloads/hand_control_20260922_125239_139000.jsonl`，2026-09-22 12:52:39 起的 A3.0 左手、Mink 记录；1,076 条 MediaPipe 原始记录、403 条有效 retarget/目标记录，有效目标时间约为记录第 24.11–52.07 秒。另核对对应诊断记录。没有开启相机/串口、没有改动控制参数或部署；只新增离线分析脚本与本报告。

本轮是 `online_control/online_motion_track` 手势项目。此前 Worker/1 kHz 工作属于 `online_control/online_motion_play` 动作播放项目，两者有独立控制入口；不能将动作播放的频率直接视作手势目标更新率。

**1. 主因：目前用“到目标点停下”的轨迹规划跟踪连续手势。**

`a30/control.py:54` 将 20 轴 `target_velocity` 和 `target_acceleration` 设为零；`push()` 随新手势替换目标位置。当前速度/加速度通过 `output.pass_to_input()` 连续保留，**不是每帧重新从静止开始**，但每个新目标的终点仍要求停下。目标不停移动时，受到速度、加速度和 jerk 限制的规划输出会持续落后。

`a30/control.py:36` 使用 1.5/2.5 rad/s、15 rad/s²、120 rad/s³；`online_control/shared/downlink.py:17` 使用整手 `Synchronization.Time`，不同手指还受到同步到达时间的耦合。普通位置目标跟踪连续信号会有滞后，Ruckig 官方也在 [Tracking Interface](https://docs.ruckig.com/tutorial.html) 一节说明这一点；不能简单把采样周期缩短当成跟踪算法改变。

用日志中同一批避碰后目标，保留约束，单独离线运行 Ruckig，即使没有相机、网络、USB、实时碰撞检查，也复现了主要滞后：

| 小指关节 | 记录中的输出 | Time / 2 ms 回放 | Time / 1 ms 回放 | No 同步 / 2 ms 回放 |
| --- | ---: | ---: | ---: | ---: |
| MCP | 265 ms | 255 ms | 255 ms | 230 ms |
| swing | 275 ms | 270 ms | 265 ms | 250 ms |
| PIP | 285 ms | 285 ms | 280 ms | 260 ms |
| DIP | 255 ms | 255 ms | 250 ms | 220 ms |

Time/2 ms 回放与日志输出的小指平均绝对角差约 0.30–0.66°。这支持 Ruckig 跟踪段是主要来源。取消 Time 同步仅减少小指约 20–35 ms，不能单独解决全部问题。1 ms 回放仅改变约 0–5 ms 相位滞后，也不能解决主因；两个采样周期的瞬时轨迹并不完全相同，角差 p95 约 0.44°、最大约 6.19°。

**2. 固定开启的 One Euro 滤波会再增加相位滞后。**

`online_motion_track/main.py:120` 固定 `min_cutoff=1.5, beta=.25, derivative_cutoff=1`。对米制 world 坐标应用该参数，低速时约 1.5 Hz 的低通截止频率，对应时间常数约 106 ms；这不等于每帧增加固定 106 ms。实际本记录的指间弯曲波形重放得到约 35–55 ms 相位滞后。world 和 normalized 是两条并行滤波支路，不能当成两次串联 world 滤波重复累加。

**3. 识别、求解、显示被串成一轮，有效目标和模型显示只有约 15 Hz。**

`static/app.js:567–675` 的顺序是：抓视频帧 → 等待 MediaPipe → 等待 `/api/frame` → 更新模型 → 才预约下一视频帧。这样不会积压旧帧，但吞吐量取决于整轮耗时及下一视频帧回调。

`a30/session.py:68` 把响应的 `pose` 替换为 `ruckig_joint_angles_rad`；`static/app.js:641` 用它更新模型。识别期间，100 ms 状态轮询的 `viewer.setPose` 又受 `!active` 条件限制，因此 Three.js 即使以 60 fps 渲染，也通常只收到约 15 次/秒的新姿态。`viewer.setPose()` 本身是直接设置姿态，没有额外缓慢插值。模型和真机一起落后手势与这条数据通路一致。

**4. Mink 在部分动作上造成额外限幅/保持，而非普遍算不动。**

403 个有效目标中，280 次 clear、59 次 limited、64 次 held_distance_check，约 30.5% 存在限制或距离检查受阻。`mink_guard.py:85–123` 在路径不满足间距时回退/保持安全结果；held 状态也可能已推进部分合法步，并不代表整帧完全不动。最大关节修正 14.24°。Mink 计算中位 1.31 ms，p95 15.70 ms，某些帧会增加尾部延迟，但不能解释普遍的约 250 ms 滞后。

另有 8 条轮询记录显示采样碰撞限制。该会话记录第 29.8838 秒出现“跟踪保护已阻断下发，请重新开启”，约为本地 12:53:09；后面仍有模型预览。这是一次保护停发，需要和“跟随慢”分开看，不能把后续预览 `h7` 事件当成真机持续运动。

## 建议处理顺序

1. 优先对手势专用轨迹策略做离线对比：有界目标速度估计/短期预测、Time 与非同步/分组同步。保留速度、加速度、jerk 上限，保持状态连续，并对改变后的中间路径继续做碰撞检查。现有回放只证明 No 同步有部分改善，没有验证新的实机碰撞路径。
2. 按米制关键点重新评估 One Euro 动态参数，比较相位误差和静止抖动；不要直接关闭全部滤波。
3. 将抓帧/识别与服务端求解解耦为有界“只保留最新帧”的流水线，并让模型按最新规划样本独立刷新，避免目标/显示都等待整轮识别完成。
4. 对 held_distance_check 集中的具体碰撞对检查代理模型和距离参数。保留碰撞保护，不能以一律关闭 Mink 作为提速结论。

当前主要问题没有证据指向 USB 包频率不足；继续优先压缩串口间隔，对这段上游跟踪滞后帮助有限。运行进程与工作区还应区分：检查时本地 8766 进程起于 12:52:24，而控制源码后续有更新；本次没有重启正在使用的服务。
