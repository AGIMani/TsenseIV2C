# A3.0 浏览器恢复看门狗与日志封存修复

日期：2026-09-22。依据 `hand_diagnostic_20260922_165827_285000.jsonl`。

## 已确认的故障链

- 北京时间 17:11:11.193，本机角度记录达到 256 MB。
- 17:11:12.585，`stale_after_pacing` 样本年龄 953 ms，开始自动重新规划。
- 17:11:12.586，浏览器接收看门狗仍按旧的 150 ms 阈值执行 disarm，累计位置写入 17749 帧。
- 17:11:12.600，重新规划接口成功返回，耗时 14.9 ms；由于已经 disarm，返回结果不能重启控制。
- 当时串口连接有效、tx_failed=0、最新遥测年龄约 1 ms，服务器 target_ready=true，无碰撞保持手指。

旧恢复代码仅豁免写入看门狗，没有豁免接收看门狗。记录满额后自动执行 IndexedDB 全量读取与大 Blob 创建，是页面停顿的可疑诱因；原日志没有 Long Task/GC 计时，不能把全部停顿时间确定归因于导出。

## 修改

1. A3 二进制流恢复使用独立的 **2 秒总期限**，覆盖重新规划请求和新流的首个有效位置写入。普通状态轮询不会延长期限。恢复完成记录 `trajectory_recovered`；真正恢复失败仍停止。
2. 不论延迟后先执行旧样本回调还是看门狗，都丢弃旧流并发起一次恢复。恢复期间不切换电机电源。用流代次检查取消旧的发送等待，防止其在新规划开始后继续写入旧报文。
3. 正在执行 USB 位置写入时不从不确定的起点重新规划；电机故障、手动停止、报文校验错误和实际写入故障继续阻断。人工停止后的晚到恢复结果不会重新开启。
4. `LocalRecorder.stop(..., {exportFile:false})` 只封存待写分块与元数据，不读回整份日志、不创建下载 Blob。容量错误回调使用此方式；结束控制后再生成原记录下载文件。历史记录导出在下发或找零期间提示先结束操作。
5. 正常结束录制仍按原流程导出；`session_end` 不再因跨过容量边界递归触发停止。已封存记录仍可在历史列表恢复。

运动速度、位置边界、碰撞检查没有放宽。发送等待仍可能受浏览器调度影响；积压时通过取消旧流并重新规划恢复，不保证浏览器硬实时，也不把过期轨迹直接补发。
