# Form2 参考流程、位置跳变断连修复及 9 月 21 日日志分析

## 修改

动作页原有 `PositionGuard.check` 将当前关节与最近成功写入比较，阈值为
`max_velocity * 0.004 + 0.000015` rad。速度为 2.5 rad/s 时约 0.574°，
1.5 rad/s 时约 0.345°；与实际经过多久无关。触发后抛异常，外层调用
`disconnect`，因此显示“位置连续性保护……需重新连接”。网络合并/跳过中间
采样也可能触发，不能据此判断 USB 物理断开。

依照用户要求取消该跳变检查和位移差驱动的附加等待。浏览器保留有限值、CRC、
会话、时效校验，只在成功写入后记录位置。动作目标继续通过服务端 Ruckig。
Qt Form2 的实际流程是目标更新 → Ruckig → DownlinkGuard 限幅 → 协议转换/USB；
限幅会同步规划起点，写失败会恢复最近成功姿态，而非因为采样跳变关闭串口。
网页版 V2 复用 Form2；A3 使用独立 20 关节规划器，并未变成与 Qt 完全相同的实现。
本次没有更改各模型的速度、加速度、jerk 参数。

动作页和 A3 手势页增加/统一 2 ms 位置包节拍，避免成批到达时突发写入。
手势页保留已有“丢弃异常样本并从最近下发姿态重新规划”的恢复流程，不因
样本跳变主动关闭 USB。手势页的运动限速仍可能要求等待超过 2 ms。
增加成功位置写入起始间隔统计：p50/p95/p99、最大值和 1–3 ms 占比。
这能验证浏览器调用节拍，不能证明 H7 每包接收间隔；没有进行物理设备驱动测试。

## Ruckig 是否平滑

有。Ruckig 限制速度、加速度与 jerk，目标变化时在线生成连续轨迹。
平滑和 USB 发送定时是不同环节；500 Hz 平均吞吐并不意味着每包恰好间隔 2 ms。
手势页显式选择关闭 Ruckig/直接模式时不走相同的 Ruckig 路径。

诊断日志对 `usb_tx`/`downlink` 等高频事件约每秒抽样一次，不能直接拿相邻
日志行计算真实包间隔。晚间约 500 Hz 来自每秒状态中的累计发送计数差。
三份完整控制日志恰好未覆盖实际连续位置发送，不能用它们证明 1–3 ms。

断开至少有两类：服务会话失效/停止流程主动关闭，以及浏览器报告设备丢失。
两次真正的设备丢失均在停发以后出现，不能仅凭这些日志归因为发送频率过高。
当时约 23.6–23.9 V、51–54.5°C 的稀疏板级遥测不足以排除瞬态掉电。
究竟是 USB 线缆、驱动、电源还是 H7 固件复位，需结合 Windows 设备事件及
H7 复位原因/接收时间戳；现有日志不支持指定其中一个为确定根因。
