# 2026-09-23 A3.0 稳态耗时与偶发卡顿修复

本次对应链路报告中的两个运行问题：稳定运行时的额外计算/抓帧等待，以及日志负担和样本积压造成的长尾卡顿。冷启动不在本次范围。没有提高 Ruckig 速度、加速度、jerk 或关闭碰撞检查。

## 改动

1. **正运动学按树深度批量计算。** `TsenseI_retargeting/fk/numpy_kinematics.py` 原先每次 FK 都逐关节做 Python 矩阵循环；现在同一深度的各手指关节用 NumPy 批量矩阵计算，雅可比的轴/原点也批量求取。保留固定关节、转动关节、移动关节及 mimic 关系，未改 retarget 的目标函数、求解迭代数和收敛条件。

2. **识别结束时及时消费已解码的新图像。** `static/app.js` 若发现视频时间已变化，就立即安排下一张最新图像的处理，避免额外等待一个 requestVideoFrameCallback 周期；视频时间没变化则继续等视频时钟。仍只有一次推理在途，不排队积累旧图。增加 `capture_timing.bitmap_ms / worker_roundtrip_ms / capture_to_detection_ms`，以后可直接区分图像拷贝与推理线程往返时间。本次没有更换 MediaPipe 模型或宣称其单次推理计算本身已经变快。

3. **完整角度日志移出主线程。** 新增 `worker-recorder.js` / `recording.worker.js`。事件发生时仍由主线程分配 seq 和时间戳，postMessage 立即取得数据快照；Worker 内沿用原 LocalRecorder 的 JSONL 格式、IndexedDB 和导出逻辑。每次实际下发、转换及遥测仍记录，不通过静默抽样换速度。相机/UI/USB 回调不等待 JSON 序列化、存储或 Blob 导出。未确认处理的事件最多 2000 条，超过即封存记录并提示，避免日志队列无界增长；记录故障会标记导出不完整。

4. **验证已有恢复修复。** 开始本次工作时，工作区已具备“达到 256 MB 后只封存、结束控制后导出”和“样本/主线程卡顿后重规划，恢复总时限 2 秒”的修复。本次保留并通过真实浏览器测试，未将这两处既有改动冒充新增算法。正常恢复从最后成功下发位置重新规划；设备明确故障和不确定的 USB 写入仍不会被无条件重开。

5. **修正下发节拍的累积误差。** 原等待逻辑以最后一次 USB 写入完成为起点，再等待 `abs(delta_q)/max_velocity`，会把本次 USB 写入耗时额外叠加到每个规划周期。现在记录真正进入 writer.write 的起始时刻，按指令发起间隔进行节拍控制；成功完成时间仍用于看门狗和恢复起点。回归测试模拟每次写入 0.6 ms、规划周期 2 ms、弯曲关节按 4 rad/s 变化，连续 40 个采样不再额外积累写入耗时。没有跳过任何位置采样、放宽关节约束或改变硬故障判断。

没有随意丢掉中间轨迹点来追赶网络队列，也没有提高速度限值去消除积压；碰撞安全检查和下发速率保护继续生效。

## Ruckig 限速对真机的影响

会影响。发送给设备的位置指令来自 Ruckig 输出，因此限速会限制目标角度每秒能变化多少。当前弯曲关节为 4 rad/s，约 229°/s；实际电机速度仍取决于驱动器、机构传动、负载和跟踪误差，软件目标限速不能替代实机速度测量。

加速度与 jerk 决定起步和换向的快慢，20 轴 Time 同步还可能让较快关节等待较慢关节。单纯把 USB 下发频率从 500 提到 1000 Hz，不会把 4 rad/s 变成 8 rad/s。

用当前 Ruckig 库算单关节、起止速度/加速度均为零、加速度 30 rad/s²、jerk 200 rad/s³：

| 位移 | 速度上限 2.5 rad/s | 速度上限 4 rad/s |
| --- | ---: | ---: |
| 0.2 rad，约 11.5° | 317.5 ms | 317.5 ms |
| 1.0 rad，约 57.3° | 623.6 ms | 542.9 ms |

短动作尚未加速到速度上限便要减速，所以只提高 max_velocity 不一定更快。这些是单关节离线规划时间，不是整手实机到位测试；连续手势也不是每一帧都从静止开始，规划器正常保留速度/加速度状态。
