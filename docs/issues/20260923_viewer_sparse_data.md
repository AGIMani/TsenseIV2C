## 结论

## 为什么诊断日志少

`online_control/online_motion_track/static/diagnostic-logger.js` 的 `SAMPLED` 集合包含 mediapipe_raw、retarget、telemetry 等事件；`controlEvent()` 对普通样本执行 1000 ms 节流。错误下发、hold 等情况有例外，不能将它理解为任何事件都严格只有每秒一条。

该文件实测：retarget 相邻采样间隔中位数 1025.2 ms，遥测 1000.2 ms。retarget 有效采样集中在 9.709–57.848 s 与 648.549–702.443 s；横轴全范围中间大片空白来自文件内没有对应 retarget 记录。查看器将超过 0.3 s 的间隔断开，98 条 retarget 显示为离散点，未插值制造连续动作。

这份文件没有 mediapipe（滤波后输入点）或 h7 事件。因此选“Retarget 输入”没有关键点，勾选 H7 也没有该阶段曲线。原始点存在于 mediapipe_raw，不能冒充处理后输入点。

## 为什么 256 MiB 控制日志只有四十多秒

`session_end` 明确记录：reason=recording_error，duration_s=43.9117999，错误信息为达到 256 MB，dropped_events=0。`local-recorder.js` 的限制为 256*1024*1024；达到上限时保留当前记录并写结束事件，所以最终文件略超过阈值。

空间主要用于高频控制与回传：telemetry 76.95 MiB、h7 60.19 MiB、conversion 50.14 MiB、downlink 42.59 MiB、usb_tx 16.52 MiB。文件行数并不等于识别帧数。

该段 retarget 的相邻间隔中位数 50.8 ms，约 20 Hz；H7 中位间隔 2.1 ms。高频轨迹目标不会每条都触发一次视觉识别。816 次原始检测中 777 次检测到手，38 条 retarget_skipped 明确为 no_hand；776 帧成功 retarget 均已加载。不能要求 76,541 行全部变成 retarget 数据点。

原始 4375 帧遥测中，当前解码器复核发现 4374 帧带异常字段；缺失值按空值处理，因此个别电机字段点数可能少于遥测帧数。这与 JSON 解析失败不同。

## 查看器修复与验证

- 加载时保留仍有效的关键点数据源；若所选阶段不存在，自动选择文件实际具有的 world / normalized / input 数据，并匹配有数据的原始手序号。
- 明确提示诊断日志为低频抽样、当前各类记录数以及 H7 阶段缺失。
- 提示腕坐标系关键点 0 的全零曲线是有效原点数据；选择指尖等点可观察变化。
- 诊断导出没有 session_end 时显示“诊断快照”，不再暗示文件缺尾；控制录制的 recording_error 显示为“记录提前结束”。

`node tests/test_control_log_viewer.cjs` 通过，新增覆盖诊断数据源切换、仅第二只手有点、原始数据源偏好保留、null 不补零和腕原点提示。用实际 Chrome 无头浏览器分别加载用户两份完整文件，均无 pageerror；控制日志所有图表有数据，诊断关键点图自动切到 world 后有数据。手工降采样只用于绘制密集曲线，retarget 的 776/98 个原始点均保留。

本轮修改查看器，不改变录制频率、大小上限、识别滤波、下发或真机控制。重新打开本地 HTML 或刷新 /data-viewer 后加载文件即可使用；已达到上限之后未写入的控制数据无法从现有文件恢复。
