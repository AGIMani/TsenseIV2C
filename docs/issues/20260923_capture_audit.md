# 2026-09-23 Retarget 数据捕获检查与修复

## 数据证据

本次重点文件位于用户 Downloads，未修改原始数据：

| 文件 | JSON 行 | MediaPipe 原始帧 | Retarget | 跳过求解 |
| --- | ---: | ---: | ---: | ---: |
| `hand_control_20260923_202058_949000 (1).jsonl` | 76,541 | 816 | 776 | 38 |
| `hand_diagnostic_20260923_201014_659000.jsonl` | 1,006 | 113 | 98 | 18 |

两文件均无 JSON 解析错误，已有 `seq` 连续。完整控制文件的 776 条 retarget 均含有效关节数值。控制文件大小 268,438,750 字节，结束时间 43.9118 秒，`session_end.reason=recording_error`，错误为达到 256 MB。之后继续控制不等于继续完整记录，已经停止采集的数据不能从这个文件恢复。

该文件的数据量主要来自 telemetry 76.95 MiB、h7 60.19 MiB、conversion 50.14 MiB、downlink 42.59 MiB、usb_tx 16.52 MiB。高频控制事件把文件推到容量上限，并非 retarget 没有产生。没有为缩小文件而对这些控制流做降采样。

816 个原始帧中，776 个有 retarget，38 个明确为 `no_hand`。剩余是 frame 0 和 40：frame 0 推理耗时 573.9 ms，超过队列原有 120 ms 年龄限制；frame 40 位于 frame 39 请求运行期间，随后 frame 41 到达，时序符合 pending 替换。旧日志没有逐帧队列丢弃事件，frame 40 的具体原因是基于代码与时序的推断。新版本直接记录原因。

诊断记录的高频事件按类型约每秒抽样，且跨越多次识别启停，不能用它的原始帧数和 retarget 数做逐帧守恒检查。旧控制日志 `dropped_events=0` 为写死值，不能据此声称整次控制零丢失。

## 检查链路与发现

1. `main.py:WebSession.process` 返回原始 `retarget_joint_angles_rad`；A3.0 包装层只改规划后 pose/actuation，保留原始 retarget 字段。V2 响应也保留原始求解结果。
2. V3 管线的 `_hold(retarget_pose=...)` 和 V2 控制门控允许“已有求解结果、tracking=false”。旧 `app.js` 使用 `rawPose && update.tracking` 保存 retarget，把这类结果错误归为跳过求解。这是独立于本次文件容量截断的真实漏记条件；不能从旧文件反推出被漏掉的具体角度。
3. MediaPipe 原始帧先记录再进 `LatestFrameQueue`。队列只保留一个请求和一个最新 pending 帧，旧版替换、过期、停止和失败没有逐帧终结记录。
4. 完整记录通过 Worker 写 IndexedDB；诊断记录使用独立库并抽样。前端创建服务会话时 `recording:false` 表示不在计算服务器重复写日志，本机是否记录由“记录角度”复选框决定。
5. 本机记录器原来 256 MiB 总量限制导致所有类型同时停录；export 方法自身未确保刷新尾部，依赖调用者先 flush。源消息克隆失败和队列积压也未计入真实丢弃数。
6. Qt 的 `ControlSessionRecorder`、服务端管线 `SessionRecorder` 是不同存储路径，不能当成浏览器日志的后备副本。本次提供文件的 metadata 明确为浏览器 Web Serial / IndexedDB；本次修改集中在实际使用的浏览器链路，未改 Qt 控制行为。

## 修复

- 有非空且有限数值的原始求解结果即保存 `retarget`，附 `tracking`、`control_accepted`、message。只有控制接受时保存新的 `control_target`；求解存在但控制拒绝时保存 `control_target_skipped`。无结果、空字典、null/NaN 数值均显式记录原因。控制安全判定保持原逻辑。
- 队列为替换、过期、关闭、取消请求、请求失败逐帧记录 `retarget_skipped`。raw/retarget/skipped 增加 `tracking_session_id`，减少跨识别会话 frame_id 重置歧义。关闭队列不等待网络，也不把旧结果重新送入控制。
- 仅完整控制记录取消 256 MiB 总量限制。IndexedDB 中连续保存原事件，导出按约 64 MiB 分段，每段包含会话头、分段号和同一时间基准；序号保持原值。分段边界可穿过同一帧的不同阶段，因此单段原始帧数不要求等于单段结果数。
- 每次导出只读取选定分段，避免一次把整段长会话加载为巨型 Blob。历史记录保留分段目录，旧版无目录的缓存仍可导出。当前单段查看器独立打开各段，不自动合并。
- 导出主动等待已有尾部写入；新增事件类型计数和已知丢弃计数；诊断状态包含完整记录是否启用、是否活动、错误及消息进度。未有结束标记时，查看器不再默认宣称丢弃为零。
- 按 UTF-8 字节计量，约 1 MiB / 100 行 / 250 ms 刷新。保留 2,000 条 Worker 待处理消息上限，增加 64 MiB 未提交存储积压上限；磁盘失败与积压明确报错封存，不让无限缓存阻塞控制。
- 存储失败块保留在当前页面内存供恢复，新会话启动前尝试补写，失败时不静默丢弃。恢复导出标注缺失存储块；页面关闭后未落盘块无法保证恢复。
- 合并并发 start，stop 等待初始化，避免取消启动时漏封存。查看器显示分段提示和跳过原因；诊断头明确其抽样属性。

- Node 测试覆盖：正常/拒绝求解保存、无手/错手/无效值、队列替换/过期/错误/取消、源事件序号、线程积压、失败通知、并发初始化、停止与导出。
- `tests/recording-browser.mjs` 启动独立 localhost 测试页面，用真实 Chrome 模块 Worker 与 IndexedDB 写入超过旧上限的约 270 MiB 数据。5 段合计 1,082 条 retarget，跨段事件序号连续，无丢失/重复；最大单段约 63.03 MiB。新 Worker 可恢复历史末段，结束标记存在。
- 同一浏览器测试覆盖活动记录未 flush 的尾部导出、源数据克隆失败计数（1 条）、模拟 QuotaExceededError 后失败块恢复且不重复。
- 查看器原有测试和新增分段/跳过原因测试通过。新增下载 UI 测试检查分段选择与文件名。
- 未连接真机、未部署 node0。没有调整滤波器、求解参数、控制频率或安全阈值，也没有在控制路径加入等待；这些采集验证不构成真机端到端延迟增加不超过 5% 的实测证明。

运行 `npm run test:recording`（在 online_motion_track 目录），以及仓库根目录 `node tests/test_control_log_viewer.cjs` 可复核。首次使用需刷新实际服务的前端；若仍访问未更新的远端页面，本地修改不会在那里生效。结束后下载全部分段再删除缓存，诊断文件仍用于低频排障。
