# V2 网页手势跟随延迟分析：14:21 录制

后续已依据 14:42 / 14:43 日志完成计时修复，并更新本地服务，见 [修复和验证记录](20260918_web_v2_timing_fix.md)。下文保留首次诊断时的原始结论与状态。

结论：这次最明显的秒级拖尾发生在 retarget 之后的 Ruckig 轨迹跟随阶段。当前控制循环没有实际达到默认的 500 Hz，但 Ruckig 仍每次只推进固定 2 ms，造成轨迹时间显著落后于真实时间。此外，前端串行处理使有效目标更新约为 15 Hz；部分姿态还被碰撞规划主动修改。这三个现象需要分开处理。

本次完成数据分析、曲线绘制和独立计时复现；**没有修改运行中的控制逻辑、重启服务或操作真机**。此前 V2 retarget 历史权重的修复见 [V2 求解响应记录](20260918_v2_extension_response.md)，其理想 500 Hz 离线实验不能证明网页控制线程真实达到 500 Hz。

## 源码与独立复现

1. `src/utils/ruckig_interpolator.py` 的 `_RUCKIG_DT` 默认是 `1/500`。`PhaseSynchronizedRuckigInterpolator.sample()` 每次只调用一次 `Ruckig.update()`；虽然接口有 `t` 参数，但此实现没有使用真实经过时间。
2. `online_control/online_motion_track/pipeline_v2/control_pipeline.py` 的 `_run()` 用 `threading.Event.wait(timeout)` 等待控制周期。超时后调整下次唤醒时间，但没有补偿 Ruckig 轨迹时间的落后。`_control_tick_locked()` 每次只调用一次 `sample()`。
3. 同一台 Windows 电脑单独执行 140 次 `Event.wait(.002)`：默认等待中位数 **15.285 ms**，P95 **16.025 ms**。在分析子进程内临时调用 `timeBeginPeriod(1)` 后，中位数 **2.016 ms**、P95 **2.486 ms**；结束后配对调用 `timeEndPeriod(1)` 恢复。结果与记录中的约 15 ms 间隔吻合。这个实验不证明完整碰撞/记录线程一定能达到 500 Hz，但能复现粗粒度等待的影响。
4. 单独使用当前相位同步 Ruckig，仅测试中指 PIP 从 1.2 rad 到 0 rad，保留 4 rad/s、30 rad/s²、200 rad/s³ 的原有限制：进入 5° 误差范围需要 **223 次采样**。理想 500 Hz 下是 **0.446 秒**；把相同采样次数放到这份记录第 13.923 秒后的实际控制调度上，需要约 **2.355 秒**。这是隔离后的合成阶跃实验，不是修复后的真人验证。

## 两个次要影响

**前端更新偏慢。** `static/app.js` 先等待 MediaPipe Worker，再等待 `/api/frame` 返回，最后才注册下一次视频帧回调。当前这条串行路径测得的目标间隔约 67 ms；单次推理和 retarget 各约 14 ms，叠加传输、处理和视频帧等待后会降低更新频率。它会使手感不够连续，也增加输入滞后，但不能独自解释中指的 2–3 秒拖尾。未记录完整客户端各阶段时间，不能精确拆分其余几十毫秒。

**碰撞会主动改变姿态。** 473 个目标中有 **184 个（38.9%）** 被避碰规划修改，其中 154 个报告小指/拇指接触。整段中指 PIP 最大目标修正约 12.93°，小指 PIP 最大修正约 79.61°。第 25 秒附近中指原始目标约 6.2°，规划后约 18.7°，此处就同时存在避碰约束。应区分“输出追不上安全目标”和“原始目标因接触不可直接执行”。日志中的接触来自碰撞代理，尚未验证是否存在几何代理过大的误判。

One Euro 滤波、恢复阶段降速、全手相位同步也会影响响应；本次没有把这些因素分别做消融，不能将所有拖尾都归结为某一个滤波参数。没有观察到 Ruckig 故障或 DownlinkGuard 限幅事件。

## 修复顺序与验收建议

1. 先修正控制线程的计时：Windows 使用可靠的高精度等待，同时明确真实经过时间与轨迹推进时间的关系。计时分辨率调整必须成对释放；线程超时不能通过突发发送多条旧姿态来追赶。增加实际周期、轨迹推进时间和超时计数的诊断。需要验证碰撞检查、记录开启时能持续达到怎样的采样率。
2. 保留速度、加速度、jerk 限制和每个实际输出的碰撞检查。若引入按真实时间采样，需对长时间停顿、目标更新、丢手制动、重新捕获和重新找零分别处理，不能把长停顿一次性积分成突然的大步动作。
3. 将摄像头推理与服务端 retarget 请求解耦，只保留最新待处理结果；请求仍保持有序，避免积压旧帧。分别记录推理频率、目标频率和相机到响应耗时，再优化 URDF 显示更新。
4. 同样的握拳—伸展动作重新录制，对照目标和 Ruckig 输出的阈值差；独立检查避碰介入段。真机未接入前先以预览和虚拟串口验证，不把本次分析视为真机验证。
