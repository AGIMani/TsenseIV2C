# A3.2 手套下发修复与验证（2026-09-29）

## 结论

已修复主机控制周期偏长、求解与发送争用 Python 执行时间、迟到后轨迹持续变慢的问题。代码和新版 DLL 已写入当前项目。严格逐包 1–4 ms 尚未达标，真机效果待复测。

本次按“Windows SDK 向 H7 提交整手目标”的间隔处理。记录位置在原生 `sendOnce()` 调用前后，不能代表 USB 到达时间、H7 收包时间或 CAN 电机更新周期。

## 改动

- 控制目标周期从 5 ms 改为 2 ms；正常按实际经过时间推进轨迹，单步最多推进 4 ms，避免长时间卡顿后产生大步进。
- Wuji 骨架求解放到独立进程。私有管道一次只允许一个请求；超时后销毁进程，拒绝将旧响应当成新目标。该进程不持有机械手设备。
- 原始帧记录、完整 SDK 状态序列化和日志目录查询移出控制锁的热点路径；遥测记录单独运行。
- 新增原生精简状态接口，以及一次完成整手目标设置与发送的接口，减少 Python/C++ 调用和 JSON 开销。
- 原生控制发送之间至少间隔 1 ms；错过调度期限后不额外等待完整周期。
- 每包增加 SDK 调用起止时间、序号、间隔、调用耗时和未推进的轨迹时间。网页显示低于 1 ms、超过 4 ms 的次数。
- 每次发送前检查相邻关节目标变化不超过 `最大速度 × 本次规划时间 + 2e-6 rad`，超限停止。原有碰撞、速度、加速度、jerk、输入过期、心跳和故障保护保留。
- 两路 MIT 电机减速比保持 50:1。

对于最大速度 2 rad/s 的关节，2 ms 步进上限约 0.229°，4 ms 上限约 0.458°；摆动关节的 1 rad/s 上限为其一半。这是关节角度约束，各直线电机的毫米差值还取决于机构映射。

## 部署状态

刷新网页后再手动进行真机测试。保留后端完整 `hand_control_*.jsonl`；新日志的 `control_timing.native_write_started_ns` 和 `native_write_interval_ms` 能检查每包提交时间，`planner_lost_ms` 能定位轨迹推进损失。浏览器批量接收时间不能当作包间隔。
